## 2. Fix the remaining Player learning-record editor

The current Player UI has a pause-note input and a Needs revision button, but users cannot conveniently edit all of a lesson's learning metadata directly while studying.

Add a well-integrated learning-record editor inside Player, using the existing application's shared state and persistence logic.

It must support:

- Confidence rating, with the existing 1–5 semantics.
- Revision date.
- Notes.
- Key concepts.
- Questions to investigate.
- Code reproduced.
- Exercise done.
- Built example.
- Needs revision.
- Review status and, where applicable, the most recent review date.

### Required behavior

1. The editor must refer to the exact selected playlist entry, not merely the numeric position.
2. Saving metadata must not mark the video complete or verified.
3. Editing metadata must not overwrite player-observed coverage, manual completion evidence, playback notes, session history, or unrelated annotations.
4. Existing annotations must load correctly when changing videos and switching playlists.
5. Edits must survive navigation, reload, and completion toggles.
6. Avoid excessive writes and rerenders, but do not risk losing unfinished user input.
7. Show clear save/error feedback consistent with the existing UI.
8. Validate revision dates and confidence appropriately.
9. Reuse a shared annotation editor or common field component where appropriate instead of duplicating conflicting state logic.
10. Make every field accessible by keyboard and screen reader, with stable labels.

If the Player's current pause-note has different semantics from the persistent learning notes, preserve that distinction and make it clear in the UI.

Add tests proving that each field saves to the correct entry, remains correct after switching videos, survives reload, and is not overwritten by completion or player events.

## 3. Revision: preserve annotations and make reviewed lessons discoverable

Inspect the actual Revision queue membership rules, store actions, identity migration, annotation fields, review history, and navigation.

The current design can make lessons disappear from the queue once marked revised. A lesson that no longer needs review must not become impossible to find or edit.

Implement a clear separation between:

- The current review requirement.
- The date and history of previous reviews.
- The lesson's persistent annotations.

### Required behavior

- Marking a lesson revised must clear the appropriate current review flag, record the review, and preserve notes, concepts, questions, confidence, revision date, code/exercise/example flags, and history.
- Reviewing a lesson must not delete it or its annotations.
- Provide a convenient way to browse/search all lessons and previously reviewed lessons, including lessons no longer in the active review queue.
- Make the distinction between “Reviewed on [date]” and “Needs revision” obvious. A lesson may have both a previous review date and a new review requirement; explain this state instead of displaying confusing contradictory-looking indicators.
- Preserve the existing fast search, jump-to-position, title search, filters, and sticky toolbar.
- Ensure the “All” label clearly describes its true scope. If it currently means all queued lessons rather than all playlist lessons, rename it or provide a separate all-lessons view.
- A direct search for a previously reviewed lesson must still find its notes and allow editing.
- Prevent repeated clicks from duplicating XP or review history entries.
- Preserve date/timezone semantics of overdue review dates.
- Do not reflag every lesson merely because it has historical annotations.

Test the complete lifecycle: create annotation, flag, edit, mark revised, leave the queue, search the reviewed lesson, edit its notes, flag it again, reload, and verify all values and review history.

## 4. History: professional, human-readable statistics

The current History screenshot displays technical-looking empty metrics such as `0s`, `0:00:00`, `0 / 17`, and “Sessions in week (0).” Do not blindly replace zero with `n/a`: zero, unavailable data, incomplete data, and an empty result set have different meanings.

Inspect every statistic, duration formatter, list and date-range filter in History.

### Required improvements

- Use consistent, readable duration formatting across the product.
- Apply a suitable shared duration formatter rather than inventing a different convention for each component.
- Avoid showing bare seconds where a concise minute/second or `H:MM:SS` value is clearer.
- Use clear labels for count ratios, such as completed versus total, and distinguish manual from verified activity.
- When a selected range has no sessions, display a useful empty state explaining that no sessions have been recorded in that period.
- Retain accurate zero values where they convey real information.
- Use `n/a` only when a metric genuinely cannot be calculated, explaining why if necessary.
- Keep all displayed statistics, the session list, and per-video details scoped consistently to the selected range.
- Label intentionally all-time totals explicitly.
- Ensure timezone and cross-midnight behavior remain accurate.

Test date presets, custom ranges, empty activity, manual entries, verified entries, cross-midnight sessions, missing durations, and multiple playlists.

Verify the self-reported form from entry through persistence. After saving a valid self-reported session, confirm that the relevant statistics, session list, and per-video details update consistently. If the entry does not belong to the selected range, tell the user why it is not visible rather than silently hiding it.

## 5. Efficiency: audit the mathematics and the user experience

Do not assume the previous implementation is correct just because its tests passed.

The current screenshot shows unique content of `12m 32s` and focused study of `0s`, while content efficiency, playback utilization, and overall efficiency display `n/a`.

That may be mathematically valid, but the presentation and underlying classifications must be verified.

Read the actual formula implementation, event attribution, source filtering, aggregation paths, and UI copy. Recalculate representative examples independently.

Verify at least:

1. Content efficiency: unique content seconds divided by focused study seconds, expressed as a percentage.
2. Aggregate efficiency: ratio of aggregate eligible unique content to aggregate eligible focused study, not the mean of daily percentages.
3. Playback utilization: the intended numerator and denominator, including pauses and buffering.
4. Verified, manual, and estimated evidence selection.
5. Missing evidence and incomplete playlist metadata.
6. Zero focused time, zero playback time, zero unique content, empty ranges, and incomplete observations.
7. Cross-midnight allocation and selected timezone.
8. Daily trends and minimum-observation eligibility.
9. Scope filters for current playlist versus all playlists.
10. Behavior when manually recorded or estimated time exists without a corresponding Focus session.

Do not silently mix manual, estimated, and verified data in a metric presented as verified. Respect the existing Evidence selector and explain its semantics.

For every formula, document its inputs, denominator, evidence rules, and edge cases. Add tests using independently calculated fixtures with exact expected results.

### Improve the interface

- Give each metric a clear name and readable value/unit.
- Make undefined metrics distinguishable from a true numeric zero.
- When focused time is zero, explain why efficiency is unavailable.
- If unique content exists but no Focus study is recorded, explain what that means without suggesting that the content calculation itself is necessarily invalid.
- Explain why results differ between daily percentages and aggregate ratios.
- Avoid decorative charts or percentages that imply data exists when it does not.
- Make the Evidence and Scope filters visibly affect every relevant statistic.
- If any current calculation is wrong, repair the calculation at its domain source rather than patching the displayed number.
- Verify that efficiency metrics update following new sessions, playlist changes, evidence edits, and reloads.

The final report must state whether the current formulas were correct, which changes were needed, and which exact test cases prove correctness.
