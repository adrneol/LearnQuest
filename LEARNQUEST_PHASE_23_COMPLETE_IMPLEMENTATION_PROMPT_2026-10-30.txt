# 2. P0 — CLOUD SAVE CONFLICT RESOLUTION AND DATA SYNCHRONIZATION

This is the highest-priority implementation.

## 2.1 User-reported defect

The user experiences a persistent message similar to:

`Save conflict · reload`

The application then refuses to save several unrelated changes, including:

- Manual video completion.
- Daily goals.
- Checkpoints.
- Focus sessions.
- Other learning-record modifications.

This must be investigated and fixed at the shared persistence layer.

Do not create independent fixes for every affected feature unless the underlying architecture proves that they have separate causes.

## 2.2 Investigate the actual root cause

Inspect:

- `frontend/src/store/store.tsx` or the current equivalent.
- Cloud account bootstrap and load logic.
- Debounced save scheduling.
- Dirty collection detection.
- The account state-version mechanism.
- `GET /api/account/data`.
- `PUT /api/account/data/:collection`.
- The backend `replaceUserCollection` service.
- State-version reservations and compare-and-set logic.
- Transaction boundaries.
- Conflict handling and error mapping.
- Save cancellation and in-flight request handling.
- Multi-tab and multi-device synchronization.
- All code paths that modify collections.

Determine whether conflicts are caused by:

- Multiple simultaneous requests within one tab.
- Another browser tab saving first.
- Another device saving first.
- A stale client state version.
- A delayed or out-of-order response.
- Multiple collection writes using the same outdated version.
- An optimistic update that was not reconciled.
- A failed save leaving the client with an outdated baseline.
- Incorrect retry behavior.
- An account load or identity switch racing with a save.

Do not assume the cause. Use source evidence and tests to establish it.

## 2.3 Implement a proper conflict-resolution architecture

The required behavior is:

**A normal conflict must not force the user to refresh the entire page or lose pending work.**

Implement a safe synchronization strategy.

### A. Serialize writes

Within one client session:

- Maintain a single controlled save queue.
- Avoid overlapping writes that use the same account version.
- Ensure collection saves are ordered correctly.
- Prevent delayed responses from overwriting newer client state.
- Cancel or invalidate work when authentication changes.
- Ensure that the queue does not permanently stall after an error.

### B. Preserve a confirmed baseline

Maintain enough state to distinguish:

1. The last server-confirmed state.
2. The user's local pending changes.
3. The newest state returned by the server.

Use this information for a genuine three-way merge.

### C. Handle version conflicts

When the server returns `VERSION_CONFLICT`:

1. Do not discard the local edits.
2. Retrieve the latest authoritative server state.
3. Determine which records changed remotely.
4. Determine which records changed locally.
5. Automatically merge non-overlapping changes.
6. Retry with the latest server version where the merge is safe.
7. Present a focused conflict-resolution interface only when the same record was changed differently on both sides.

Use stable record IDs and domain-specific semantics.

Do not blindly merge arrays by index.

Do not blindly replace the latest remote collection with the stale local collection.

Do not automatically choose local or remote values when both contain different edits to the same meaningful record.

### D. Domain-specific merge requirements

Inspect the schema of each collection.

Use appropriate semantics for:

- Progress records.
- Goals.
- Checkpoints.
- Modules.
- Focus sessions.
- Playback sessions.
- Video segments.
- XP awards.
- Achievements.
- Preferences.
- Playlist records.
- Arena settings and history.

For event-like data, prefer idempotent append/insert semantics rather than replacing a large collection.

For keyed records, merge by stable identity.

For deletions, preserve deletion intent explicitly so deleted records are not accidentally resurrected during merging.

For singleton settings, define clear conflict semantics.

### E. Per-domain revisions

Evaluate introducing per-domain versions alongside the existing global account version.

A domain-level revision should prevent an unrelated update to Focus from unnecessarily blocking a change to Goals.

However:

- Preserve atomicity.
- Preserve cross-domain consistency where required.
- Maintain compatibility with current clients and imports.
- Avoid introducing multiple independent authorities for the same data.
- Do not remove the global account integrity mechanism without a proven replacement.

If per-domain revisions are too invasive for a safe first implementation, implement robust three-way reconciliation using the existing global version and document the staged path to domain revisions.

### F. Idempotency

Introduce stable request or operation identifiers where necessary.

Repeated requests after timeouts must not create:

- Duplicate focus sessions.
- Duplicate playback sessions.
- Duplicate segments.
- Duplicate XP awards.
- Duplicate completion records.

A network timeout must not leave the client guessing whether a write succeeded.

### G. User-facing save states

Replace the unhelpful reload-only conflict experience with meaningful states:

- Saving…
- Saved.
- Reconnecting…
- Changes waiting to sync.
- Resolving changes…
- A change needs your review.

A successful automatic reconciliation should simply return to Saved.

When manual resolution is required, show the affected record and its two versions with understandable choices.

Do not present the raw database revision or internal concurrency error to an ordinary user.

### H. User-data preservation

A conflict must never silently erase:

- Manual completion changes.
- Goal edits.
- Checkpoint edits.
- Focus notes.
- Session records.
- Other user-created data.

If reconciliation cannot be completed safely, preserve pending changes and provide an explicit recovery action.

Do not claim that a change was saved until the server confirms it.

Do not retry an ambiguous write in a way that can duplicate an event.

## 2.4 Save-conflict acceptance criteria

All must pass:

- Two tabs editing different Goals/Checkpoints records can save without losing either change.
- Two devices changing different domains can reconcile automatically.
- Two devices editing the same record produce a clear resolution state.
- Delayed responses cannot overwrite newer data.
- Multiple rapid edits are saved in order.
- A failed network request does not permanently poison the save queue.
- A stale account version is recovered without a full page reload.
- Manual video completion remains saved after a conflict.
- Goal, Checkpoint and Focus edits remain saved after a conflict.
- Repeated or retried requests do not create duplicate records.
- A sign-out or account switch aborts pending work for the previous identity.
- Every save result is accurately represented in the UI.

This workstream must have backend integration tests, frontend tests and real-browser multi-tab tests.

# 3. P0 — AUTHENTICATION, LOGOUT, SESSION IDENTITY AND REMOTE REVOCATION

Read Report 22 Sections 4–8 and its test matrix.

## 3.1 Preserve existing security controls

Do not weaken:

- HttpOnly session cookies.
- Secure production cookies.
- `__Host-` cookie constraints.
- SameSite protections.
- CSRF validation.
- OAuth state and browser binding.
- Session token hashing.
- Password-version checks.
- Absolute and idle expiry.
- Account-scoped authorization.
- Recent authentication for security-sensitive operations.

The server remains authoritative for session validity.

## 3.2 Same-browser synchronization

The current implementation already has BroadcastChannel and a storage-event fallback.

Preserve it and address the residual gaps:

- Broadcast authentication changes after sign-in as well as sign-out.
- Broadcast a local-clear signal even when remote logout confirmation fails, using an explicit unconfirmed status.
- Ensure other tabs clear account data, pending requests, CSRF state and focus recovery state.
- Do not include cookies, tokens, session IDs, emails or learning records in broadcast events.
- Ensure a failed logout does not misleadingly claim that the server session was revoked.

## 3.3 Cross-account tab protection

Implement an identity assertion in account-load responses.

An older tab must never display account B's data while it still believes that account A is signed in.

When an identity mismatch is detected:

- Invalidate the old load.
- Clear the old account state.
- Abort inappropriate pending writes.
- Require a fresh sign-in or explicit user action.
- Never silently switch the old tab to the new identity.

Validate the same rule for late responses and manual refreshes.

## 3.4 Remote-device logout

Implement bounded remote revocation visibility without unnecessary infrastructure.

Preferred approach:

1. Revalidate when a visible authenticated tab regains focus.
2. Revalidate on visibility change.
3. Use a modest visible-tab heartbeat, approximately 60–90 seconds, with jitter.
4. Revalidate before high-value account mutations when the prior check is stale.
5. Handle `401 SESSION_EXPIRED` and session-revocation codes immediately.
6. When offline, clearly distinguish offline/unverified state from a valid authenticated session.
7. On reconnect, revalidate before saving.

Do not build WebSockets or SSE unless the current infrastructure demonstrably requires them.

Do not poll hidden tabs unnecessarily.

Do not introduce an unbounded heartbeat or a session-touch write on every timer tick.

## 3.5 Acceptance criteria

- Sign-out from one tab clears other same-origin tabs promptly.
- Failed logout clears local private UI with an unconfirmed notice.
- Sign-out-all revokes every server session.
- A visible remote device clears its private UI within the heartbeat/revalidation interval.
- A suspended device clears on wake before its next protected save.
- Account A's tab never shows account B's data.
- Old asynchronous responses cannot restore an authenticated state.
- No authentication secret appears in browser storage or synchronization messages.

This is a required product change.

They want the email change to be verified through Google authentication, consistent with the Google-based identity flow used during registration/sign-in.

## 4.2 Required new user experience

Replace the existing form with a simple Google-authenticated action.

Suggested presentation:

**Email address**

Current verified email: `[current address]`

Button:

`Change email with Google`

Short supporting copy:

`Verify your Google account to update your email address.`

- A manually editable new-email field.
- A current-password input on the normal Google-linked account path.
- An OTP input.
- A Send OTP button.
- A Send verification link button.

The Google OAuth result supplies the verified email address. The user must not be able to type an arbitrary destination address into this flow.

After successful verification, show the email that Google returned and a concise confirmation step if needed.

## 4.3 Required security architecture

Before implementing, inspect the current Google OAuth and account identity model.

Determine:

- How Google `sub` is stored.
- How password-based accounts are represented.
- How Google accounts are linked to existing accounts.
- How email uniqueness is enforced.
- How login selects an existing account.
- Whether Google registration and login intents are separate.
- Whether email change currently revokes sessions.
- How the existing OAuth browser-binding and state mechanisms work.

Create a separate purpose-bound OAuth intent for email change.

It must be:

- Bound to the currently authenticated LearnQuest user.
- Bound to the initiating browser/session.
- Single-use.
- Short-lived.
- Protected by state validation and browser binding.
- Independent of the normal login or registration intent.

Validate the Google identity token using the project's established verification library and configuration.

Verify:

- Signature.
- Issuer.
- Audience.
- Expiry.
- Nonce/state.
- Browser binding.
- `email_verified === true`.
- A valid Google subject identifier (`sub`).

Never trust an email address supplied by the browser.

### Existing versus new Google identities

This distinction is critical.

For a LearnQuest account whose Google identity is already linked:

- Require fresh Google authentication of the linked identity.
- Use the provider's verified email claim.
- Confirm that the returned identity belongs to the currently authenticated account.
- Update the account email only after all uniqueness and consistency checks pass.

If the user selects a different Google identity:

- Treat this as an explicit account-linking operation, not merely an email edit.
- Require secure proof of control of the existing LearnQuest account.
- Bind the new Google identity explicitly to that account.
- Ensure its Google `sub` and email are not associated with another account.
- Never attach an identity based solely on matching email text.
- Never automatically merge two existing LearnQuest accounts.
- If the existing account has no Google identity and safe linking cannot be established, block the email change and explain the required secure linking step. Do not fall back to OTP.

The agent must choose and implement the secure flow compatible with the actual account model. Do not take a shortcut that creates an account-takeover vulnerability.

### Email change completion

After successful Google verification:

- Normalize the provider email.
- Validate uniqueness.
- Update the account email and verified status atomically.
- Preserve account ownership and learning records.
- Update associated Google identity metadata correctly.
- Invalidate email-change challenges that are no longer relevant.
- Apply the project's secure session-rotation/revocation policy.
- Notify the previous email address that the change occurred, where supported, but do not require that notification to complete the change.
- Never send an OTP or verification link to complete this Google-authorized change.

A Google-verified address is the source of truth for the new address.

Do not claim that every Google account necessarily uses a `gmail.com` address. Do not impose a Gmail-only restriction unless the current product policy explicitly requires it.

## 4.4 Preserve existing OTP infrastructure

# 5. P0 — FOCUS TIMING INTEGRITY AND RECOVERY

Read Report 22 Sections 12–13.

Do not merely restyle an unreliable timer.

## 5.1 Correct timing architecture

The existing implementation uses wall-clock timing and is vulnerable to:

- System clock changes.
- Sleep/wake gaps.
- Visible inactivity.
- Multiple tabs running overlapping timers.
- Multiple devices recording overlapping intervals.
- Recovery-key account contamination.
- Missing server-side cross-field validation.
- Excessively long paused sessions.

Implement the safer timing model.

### Monotonic time

Use a monotonic clock while the page lifetime is active.

Use wall-clock anchors for persistent timestamps and calendar attribution.

Important:

`performance.now()` values are relative to the current page context. Do not treat them as persistent absolute timestamps or compare raw values across reloads.

When the page is reloaded:

- Close the prior running interval at its last trustworthy persisted checkpoint.
- Exclude the unobserved interval while the page was closed.
- Restore the timer as paused or recovered.
- Require an explicit resume action.

Use the monotonic/wall-clock difference during an active page lifetime to detect clock jumps and suspicious gaps.

Implement a conservative gap policy and test it with fake clocks.

Do not silently count an unbounded sleep interval as study time.

## 5.2 Correct interval accounting

Use interval unions.

Conceptually:

`Qualified Focus = Union(valid active intervals) - Union(paused and disqualified intervals)`

The implementation must:

- Merge overlaps.
- Prevent duplicate tab intervals from being counted twice.
- Exclude paused time.
- Exclude unobserved recovery gaps.
- Reject reversed, non-finite and invalid intervals.
- Preserve the original recorded evidence where useful for history.
- Keep manual corrections explicitly marked estimated.

## 5.3 Multi-tab ownership

Use the Web Locks API where available to ensure only one tab owns the active timer for an account.

Provide a safe fallback using BroadcastChannel with an expiring owner lease.

A second tab must be told that another tab already owns the active timer.

Do not let two active timers overlap and independently add their full durations.

On lock loss, pause and persist safely.

For different devices, add overlap diagnostics and a server-side policy. Do not silently double-count overlapping focus time.

## 5.4 Server-side validation

Validate:

- `activeSec <= elapsedSec`.
- `pausedSec` matches the elapsed/active relationship.
- Interval sums match stored durations within an explicit rounding tolerance.
- Active and paused intervals do not overlap.
- Start time precedes finish time.
- Session duration is plausible.
- Repeated client IDs are idempotent.
- Manual corrections remain estimated.
- Old session schema versions remain readable.

Do not reject all existing historical records merely because they predate the new model.

Preserve legacy sessions as historical recorded data, not newly verified data.

## 5.5 Recovery and storage

- Reduce unnecessary one-second localStorage writes to a sensible checkpoint interval, approximately five seconds.
- Use a versioned timer snapshot.
- Scope recovery state to the correct account.
- Remove old account recovery data on sign-out and account switch.
- Do not expose a previous user's session note to another user.
- Preserve a draft if the final session save fails.
- Provide Retry and Discard actions.
- Do not award XP before a session save is confirmed.

## 5.6 Focus timing acceptance tests

Test:

- Start, pause, resume and finish.
- Repeated finish.
- Refresh while running.
- Browser close and reopen.
- Page hidden and visible.
- System sleep and wake.
- Wall clock jumping forward.
- Wall clock jumping backward.
- Long paused intervals.
- Two tabs attempting to start.
- Two devices with overlapping sessions.
- Account switch.
- Save failure and retry.
- Cross-midnight attribution.
- Daylight-saving boundaries.
- Existing historical sessions.

# 7. P1 — COMPLETE ARENA V2 REDESIGN

Read Report 22 Sections 9–11 carefully.

Do not preserve the old equal-weight daily-efficiency ranking as a fallback.

## 7.1 Objective

Arena should be a consistent, transparent simulation of learning progress and learning consistency.

It must remain clearly distinguished from a real-user leaderboard.

## 7.2 Recommended formula

Implement the versioned candidate:

`P = min(U / L, 1)`

`C = min(Q / W, 1)`

`Arena Score = 100 × (0.75 × P + 0.25 × C)`

Where:

- `U` = unique completed/covered playlist content seconds.
- `L` = total resolved playlist duration.
- `Q` = number of qualifying learning days.
- `W` = fixed competition-window days.
- `P` = progress ratio.
- `C` = consistency ratio.

Score must be bounded between 0 and 100.

If the denominator is unknown, the score is unavailable.

Do not manufacture playlist duration from an average when entries are unresolved.

## 7.3 Qualifying-day eligibility

Use the Report 22 proposed threshold as a versioned product rule:

- At least 300 seconds of genuine new content gain or a qualifying completed video.
- At least 600 seconds of recorded focus or active playback evidence.
- A running timer without content progress does not qualify.
- Duplicate watching does not produce additional new content.
- Autoplay without the required qualifying evidence cannot grant a qualifying day.

These are product-design thresholds, not scientifically established attention measurements.

Use only data the application actually collects.

Do not claim that timer activity or playback proves comprehension.

## 7.4 Provisional eligibility

A learner should not receive a ranked position immediately after a tiny amount of activity.

Use:

- At least 3 qualifying days.
- At least 7 observed calendar days.

Until both conditions are satisfied, show a provisional state and exclude the learner from ranked percentiles.

Do not show provisional users as last place.

## 7.5 Competitor generation

All simulated competitors must use the same scoring rules as the user.

Implement:

- Versioned deterministic seed.
- Stable rival identities.
- Realistic activity trajectories.
- Tier-specific progress and consistency profiles.
- Monotonic cumulative progress.
- Bounded content gains.
- Rest days and calendar effects.
- Stable results for identical inputs.
- No fabricated content beyond playlist duration.

Use the tier bands and sensitivity analysis in Report 22 as initial design inputs.

Do not generate competitor daily efficiency percentages independently and then calculate rank from those values.

Generate comparable learning trajectories and calculate each score through the same domain functions.

## 7.6 Fixed challenge versus practice simulation

Separate the user experience into:

**Practice simulation**

- Change competitor count.
- Change difficulty.
- Change time window.
- Generate a new cohort.
- Explore different conditions.
- Clearly label the result as practice.

**Fixed challenge run**

- Fixed start and end.
- Fixed formula version.
- Fixed seed and cohort.
- Fixed scoring weights.
- Configuration becomes read-only after the run starts.
- Historical results are not silently recalculated.

Both modes still use fictional opponents. Do not imply that the fixed challenge is a real-user competitive leaderboard.

Changing simulation settings must never change actual user progress, Focus, Efficiency, XP or achievements.

## 7.7 Score presentation

Show the score decomposition:

- Progress percentage.
- Consistency percentage.
- Progress contribution.
- Consistency contribution.
- Final score.
- Qualifying-day count.
- Provisional state.
- Evidence mix where available.

Explain the scoring model through a small expandable “How ranking works” section.

Keep the interface understandable for beginners.

## 7.8 Arena settings

Expose the useful simulation preferences without overwhelming the page:

- Intensity: Relaxed / Standard / Competitive.
- Number of opponents.
- Competition window.
- New practice cohort.
- Advanced tier distribution only when expanded.

Do not let users edit scoring weights or official/fixed challenge settings after it begins.

## 7.9 Arena tests

Test:

- One-minute exploit.
