## PHASE 5 — PASSWORD RECOVERY AND CRYPTOGRAPHIC TOKEN SECURITY

The previously agreed recovery design replaced numeric OTP recovery with secure single-use email action links. Preserve that design for password recovery; do not reintroduce a numeric OTP field or create an inconsistent mixture of link and code flows.

Audit all remaining account verification, email verification, and authentication-related OTP functionality separately.

Search the entire repository for `Math.random` and determine whether any use occurs in:
- OTP generation.
- Password-reset or email-change tokens.
- Session or authentication tokens.
- Security challenges or verification codes.

Never use `Math.random` for a security-sensitive secret or authentication credential.

For any active OTP-based flow that is genuinely required by the application's current design, use a cryptographically secure generator, such as Node's `crypto.randomInt` for a numeric code or `crypto.randomBytes` for opaque tokens.

Any remaining OTP flow must have:
- Appropriate entropy for the credential's purpose.
- Secure storage, preferably a digest/HMAC rather than the raw code.
- Short server-enforced expiry.
- Atomic single-use consumption.
- Strict attempt limits and rate limiting.
- Cooldown and resend invalidation.
- Purpose and account binding.
- Replay prevention.
- No tokens/codes in logs.
- Proper error messages that do not reveal account existence.

For password-reset links, keep high-entropy cryptographically random tokens, digest/HMAC storage, purpose binding, expiry, atomic single-use consumption, and invalidation of older outstanding tokens.

Do not weaken the password policy. Verify Argon2id password hashing and revoke existing sessions after a successful reset.

Add security tests proving that no active security flow generates tokens with `Math.random`, where the code can be tested directly.
