# 3. Redesign Checkpoint creation to remove redundant inputs

The current Checkpoints screen has separate Label, Start, and End fields. This is confusing because a user who wants a checkpoint covering videos 1–8 should not have to enter a range twice or guess what the label is supposed to contain.

Redesign this form into a natural, concise workflow.

## Required creation experience

The main form should require only one range input:

**Video range**

Example:
- `1-8`
- `9-16`
- `50-60`
- `103`

Accept reasonable spacing and standard hyphen/en-dash input.

The user should be able to type `1-8` and create the checkpoint without needing to enter the number range again in other fields.

Automatically derive the display label:

- `1-8` → `Videos 1–8`
- `9-16` → `Videos 9–16`
- `103` → `Video 103`

Add an optional, secondary custom-name field only for users who want a more descriptive milestone name, such as `JavaScript fundamentals`.

When a custom name is not supplied, the automatically generated label is the saved name. Do not require a label or display a confusing placeholder suggesting the user must name a numeric range manually.

Provide a live preview of the parsed range and resulting checkpoint name.

## Validation

- Require a valid single contiguous range or one valid position.
- Normalize `1 - 8`, `1–8`, and `1-8` consistently.
- Validate that positions fall within `1..N` for the active playlist.
- Reject malformed, negative, fractional, reversed, empty, and out-of-bounds ranges with understandable feedback.
- Do not silently clamp an invalid input into an unrelated range.
- Test the active playlist, including empty or unavailable playlist metadata.
- Preserve existing saved checkpoints and custom names when editing existing records.

Do not change the definition of an inclusive checkpoint range or award completion rewards prematurely.

## Separate checkpoints from saved ranges

The page currently mixes checkpoint creation with saved duration ranges. Explain the two functions clearly and keep them visually distinct:

**Checkpoint:** a learning milestone over a video range. Progress is tracked, completion is recognized when the full eligible range is complete, and the established milestone/XP behavior is applied.

**Saved range:** a reusable duration/range calculation saved from Library. It does not independently represent completion or award milestone XP.

Organize the page so a new user understands the distinction without reading a long explanatory paragraph.

Provide concise helper text, clear section titles, useful empty states, responsive fields, and consistent labels.

Check whether a checkpoint should navigate to the relevant range in Library or Player; implement a convenient route only if it is consistent with current application navigation and stable entry identity.

Add regression tests for parsing, naming, validation, custom names, existing checkpoint compatibility, completion boundaries, and saved-range separation.

# 4. Architectural transition: MongoDB as the authoritative user-data store

The current LearnQuest system stores its authoritative learning state in browser IndexedDB. That must change.

**MongoDB on the server must become the authoritative persistence layer for authenticated accounts.**

Adding a users collection while leaving progress, Focus sessions, Revision notes, goals, checkpoints, and analytics inputs solely in IndexedDB is not sufficient.

Inspect every stored key, store action, state transition, export/import operation, and consumer before changing the persistence boundary.

## 4.1 Create an authenticated server data architecture

Use the existing Express/TypeScript backend and its established conventions. Reuse existing abstractions where practical. Prefer the official MongoDB Node.js driver unless the current repository already has a justified data-access layer.

Implement:

- Centralized MongoDB connection lifecycle and error handling.
- Validated configuration at startup.
- Defined schemas or runtime validators for every request and stored entity.
- Explicit repositories/services for user-owned data.
- Appropriate unique, TTL, and compound indexes.
- Bounded request sizes and collection growth.
- Safe pagination for potentially large history and record collections.
- Optimistic concurrency or version checks for conflicting updates.
- Idempotency for operations that can be retried.
- Robust handling of transient database disconnections.
- Transactional or otherwise all-or-nothing behavior for multi-document operations where required.
- Safe migrations for legacy identities and backup formats.

Do not place the entire unbounded history of a user in one giant MongoDB document.

Use appropriate collections for account identity, sessions, authentication challenges, playlists, progress records, Focus sessions, playback sessions and segments, checkpoints, saved ranges, modules, goals, achievements, XP ledger entries, Revision history, settings/preferences, and any other actual state discovered in the codebase.

The exact collection design should reflect the actual domain model. Every user-owned record must have reliable ownership and identity.

## 4.2 Enforce strict user isolation

Derive the authenticated user ID from the validated server-side session, never from a client-supplied `userId` field.

Every read, update, delete, list, export, restore, and bulk mutation must be scoped to the authenticated user.

A user must never be able to access another account's information by guessing or modifying:

- Playlist IDs.
- Progress or entry IDs.
- Focus session IDs.
- Playback segment IDs.
- Revision records.
- Goal or checkpoint IDs.
- Export or backup references.
- Any other entity identifiers.

Apply ownership checks at the repository/service boundary, not only in UI components.

Never trust a client-provided ownership field, MongoDB query object, role, privilege, or account identifier.

Add two-user isolation tests: create accounts A and B with distinct learning data, then prove that A cannot read, list, update, delete, export, or restore B's records and vice versa.

## 4.3 Data migration from the existing local-first app

Current users already have data stored in IndexedDB. Do not silently discard it or mix it into an unintended account.

Implement an explicit one-time local-to-account migration workflow.

1. A visitor can register/sign in.
2. After authentication, detect whether legacy local LearnQuest data exists without exposing the underlying learning records on the login screen.
3. If import is available, offer a clear migration dialog describing what will be transferred and how it will be handled.
4. Allow the user to download a backup before migrating.
5. Validate and stage the complete local dataset.
6. Migrate playlists, stable identities, progress, annotations, Focus sessions, playback evidence, goals, checkpoints, modules, saved ranges, Revision history, preferences, achievements, XP, and all other persistent state.
7. Preserve duplicate playlist occurrences and the stable entry identities introduced by prior remediation.
8. Make retrying a failed migration idempotent; do not duplicate sessions, XP, or annotations.
9. Mark migration complete only after the server confirms that all intended data has been stored successfully.
10. If the migration fails partway through, retain the source data and offer recovery. Never claim complete migration after a partial upload.
11. Show a clear summary of what was imported and any conflicts or items that could not be migrated.
12. Do not overwrite existing cloud records silently. Define deterministic conflict rules and explain them.
13. Offer a clear choice for retaining a local backup or removing legacy local data after the successful import has been verified and the user confirms the cleanup.

The application must distinguish unclaimed legacy data from data already migrated to a specific account. A different user signing in on the same browser must never accidentally inherit another user's data.

After account migration, authenticated data must be served from MongoDB. Do not silently fall back to a separate local-only account state when the network or backend fails.

## 4.4 Local caching and sign-out

Do not persist authenticated user records as unscoped browser data.

Prefer in-memory caching for authenticated state. If any persistent client cache is truly necessary, namespace it by authenticated user, document the purpose, and clear it on logout/account switching.

At logout:

- Invalidate the server session.
- Clear in-memory account data and query caches.
- Clear any transient client data that could reveal the previous account.
- Reset account-specific UI state.
- Ensure the next user cannot see the previous account's profile, playlist, annotations, or statistics.

Preferences that belong to an account must be stored on the server. A harmless device-only navigation preference may remain local if it is genuinely independent of user identity.

Provide explicit loading, offline/unreachable, retry, authentication-expired, and save-failure states. Never report a cloud save as successful before the backend confirms it.

Make the backend the source of truth for synchronization and conflict resolution. Document that full offline editing is not available unless a properly isolated offline architecture is deliberately implemented.

## 4.5 Data export, deletion, and recovery

Preserve the existing JSON backup concepts while moving the authoritative state to accounts.

Provide an authenticated user export containing the user's learning data, with a supported schema version.

Implement account deletion with clear confirmation and recent reauthentication. Remove the account's data and associated sessions consistently; do not leave accessible orphaned records.

Ensure session revocation, backups, and delete behavior do not accidentally expose another user's data.

# 5. Authentication model and sign-up requirements

Registration must be through Google authentication only. Do not provide a manual email-and-password registration form.

The sign-up flow must derive the initial email address from the validated Google identity. The user must not type any arbitrary email address into the signup form.

Google authentication must also remain an available sign-in method for existing linked accounts.

## 5.1 Registration flow

A new user selects:

**Continue with Google**

After the backend validates the Google authentication response:

- Identify the Google account using its stable `sub` claim.
- Require a verified email claim for initial account registration.
- Check username/email uniqueness and account status safely.
- Create an account in an onboarding-incomplete state.
- Show a professional first-time setup flow for:
  - Username.
  - Display name.
  - Setting an initial password.
  - Relevant learning preferences, such as display timezone and session defaults.
- Validate all values server-side.
- Complete the profile only after required fields are valid and saved.
- Then take the user to LearnQuest.

Persist the new account and its preferences in MongoDB.

If onboarding is interrupted, the authenticated user must be able to resume it safely.

A Google identity must not create multiple accounts simply because its email changed. Use the provider's stable subject identifier.

Do not automatically link a previously existing account to a different Google identity merely because the email strings match. Require a safe authenticated account-linking flow if linking is ever supported.

Google email verification reduces disposable-account abuse but does not prove that an email address will remain permanent. If a disposable-domain policy is desired, make it an explicit server-side policy and do not claim absolute prevention.

## 5.2 Sign-in flow

Provide two clear paths:

1. **Continue with Google** for an existing linked account.
2. **Username or email + password**.

The identifier input must accept either the registered username or registered email.

Normalize usernames and emails consistently for lookup. Preserve the intended display form while preventing case-based duplicate accounts.

Do not reveal whether a particular email or username exists through error messages, password reset responses, or timing differences.

A successful login must rotate/regenerate the session identifier. A failed login must not reveal credentials or tokens in logs.

Require the first-time password setup described above for newly created accounts if password login is part of the registration experience. Google login remains available.

## 5.3 OAuth/OIDC security

Use a standard, maintained Google OpenID Connect flow appropriate to this architecture.

Implement and verify:

- State parameter validation.
- Nonce validation.
- PKCE where applicable to the chosen authorization-code flow.
- Exact redirect URI validation.
- Signature verification of ID tokens.
- Issuer, audience, expiry, and other required claim checks.
- Verified-email handling.
- Stable `sub` identity.
- Protection against replay, callback forgery, and account-linking mistakes.
- Single-use OAuth state and safe error handling.
- No OAuth access token, refresh token, client secret, or session credential written to localStorage or exposed in logs.

Do not accept a client-supplied email/username as proof of identity.

# 6. Password and session security

Use current maintained libraries and established security controls; do not design a custom cryptographic or session protocol.

## 6.1 Password storage and changes

Use Argon2id for password hashing where supported by the deployment runtime and maintained library choice. Use a strong salted, versioned hash configuration.

Never store plaintext passwords or reversibly encrypted passwords. Do not use a single fast SHA hash for password storage.

Validate passwords server-side, enforce sensible length limits, support password managers and paste, and avoid unnecessary composition rules that encourage weak patterns.

Provide authenticated password change:

- Require recent authentication or the current password.
- Verify the current credential when applicable.
- Store only the new password hash.
- Invalidate or rotate sessions as appropriate.
- Notify the account email of a security-sensitive password change.
- Never log the submitted password.

## 6.2 Server-side sessions

Use server-side sessions stored in MongoDB or another deliberate server-side session store. Do not store the full session object in a client-readable cookie.

Do not store JWTs, refresh tokens, passwords, or session credentials in localStorage/sessionStorage.

Use a high-entropy session identifier and a production cookie with the following properties where the deployment topology permits:

- `HttpOnly`.
- `Secure` in production.
- Explicit `SameSite`.
- A host-only cookie with `Path=/`.
- A non-revealing cookie name; use a `__Host-` prefix when its restrictions can be satisfied.
- Server-enforced absolute and idle expiry.
- Session invalidation on logout, password reset, and other appropriate security events.

Regenerate session IDs after login, Google authentication, onboarding completion, and privilege-sensitive changes.

Implement:

- Logout that invalidates the server session as well as clearing the cookie.
- Logout all sessions.
- Protection against session fixation.
- Session expiry and cleanup.
- Session revocation after password reset.
- Recent reauthentication for sensitive account changes.
- `Cache-Control: no-store` for sensitive authentication responses.
- Appropriate protection against CSRF on state-changing endpoints.

### Cross-origin deployment

Inspect the real frontend/backend deployment architecture before choosing cookie settings.

Do not silently rely on cross-site third-party cookies that major browsers may block. Prefer a same-site deployment/custom-domain arrangement or a properly configured same-origin API proxy if the current hosting configuration permits it.

If separate cross-site frontend and API origins must be used, explicitly evaluate credentialed CORS, cookie requirements, CSRF defenses, Google OAuth callbacks, and modern browser restrictions. Document and test the chosen approach rather than assuming the cookies will work.

Never use wildcard credentialed CORS. Never trust the `Origin` or forwarded-IP headers without an appropriate validation/trust policy.

## 6.3 CSRF and request security

Use a well-understood CSRF defense for state-changing cookie-authenticated requests. Enforce an exact allowed origin and a server-validated CSRF token where appropriate.

SameSite is defense in depth, not the sole CSRF control.

Validate content type, request size, schema, ownership, and method semantics on the server. Do not perform state changes via GET requests.

Use Helmet and an appropriate production security-header policy without breaking required Vite assets, Google authentication, YouTube embeds, or the API.

Evaluate a real production Content-Security-Policy configuration and document what still needs browser testing. Do not blindly ship a restrictive policy that breaks the product.

# 7. Brevo transactional email and six-digit OTP

Use the Brevo transactional email API for password-reset OTPs and new-email verification.

Read the official API documentation:
https://developers.brevo.com/docs/send-a-transactional-email

Implement a reusable email service with a professional LearnQuest HTML email template and a plain-text alternative.

The emails should include:

- LearnQuest branding.
- Clear subject and heading.
- The six-digit code.
- A clear expiration time.
- A warning never to share the code.
- A statement that the user can ignore the email if they did not request the action.
- Responsive layout and inline styles suitable for email clients.
- No unnecessary tracking or external asset dependency.
- Safe escaping of all dynamic values.
- Both HTML and plain-text message content.

Use the Brevo API key only on the backend. Never expose it in the frontend, build artifacts, error messages, or logs.

Handle Brevo errors, timeouts, and rate limits safely. Do not reveal OTP values through debugging messages.

## 7.1 OTP generation and storage

Use cryptographically secure randomness such as the appropriate Node.js crypto API. Do not use `Math.random()`.

For each challenge:

- Generate a six-digit numeric OTP using a cryptographically secure generator.
- Store only a keyed digest/HMAC or similarly secure verifier, not the raw code.
- Bind the challenge to the user, purpose, target email where applicable, and expiry.
- Use a short expiry, such as 10 minutes.
- Limit incorrect attempts, such as five attempts per challenge.
- Apply resend cooldowns and per-account/IP rate limiting.
- Make codes single-use and invalidate superseded challenges.
- Prevent an OTP issued for email change from being accepted for password reset, or vice versa.
- Use constant-time comparison for stored digest verification where appropriate.
- Consume the code atomically so concurrent requests cannot reuse it.
- Ensure expired/used challenges cannot succeed after retries or server restarts.
- Never store a raw OTP in an audit record or log.

Set concrete limits in validated configuration or well-defined constants, and cover them with tests.

## 7.2 Forgot-password flow

Implement an accessible **Forgot password?** flow.

1. User enters their registered username or email.
2. The response is generic and does not disclose whether an account exists.
3. If an eligible account exists, send its registered email a six-digit OTP using Brevo.
4. The user enters the OTP.
5. The backend validates its purpose, expiry, attempt count, target account, and single-use state.
6. After successful verification, permit the user to set a new password.
7. Revoke existing sessions as appropriate.
8. Notify the account holder that the password was reset.

Do not let a browser decide that an OTP is valid. All verification and password changes must occur server-side.

Do not issue a password-reset token merely because the client returned a previously entered email or username.

## 7.3 Email-change flow

In Account Settings:

1. The authenticated user requests an email change.
2. Require recent reauthentication where appropriate.
3. Validate and normalize the proposed new email.
4. Verify that it is available for the account.
5. Send a six-digit OTP to the new address.
6. Keep the old address active until successful verification.
7. Atomically verify the challenge and update the account email.
8. Notify the old email about the change.
9. Invalidate stale challenges and rotate/revoke sessions as appropriate.

The Google identity remains linked by its stable provider subject; changing LearnQuest's account email must not break Google login or silently replace the linked Google identity.

Do not claim success until verification and the database update have completed.

# 13. Security acceptance requirements

Treat account ownership and session handling as high-risk code.

Test for:

- User A cannot read or mutate User B's records.
- Session IDs rotate on authentication and cannot be reused after logout/revocation.
- Passwords are never stored in plaintext.
- Google identity cannot be forged by supplying an email from the client.
- OAuth state, nonce, callback, and token validations reject invalid cases.
- Signup and login races cannot create duplicate users.
- Email change cannot be completed without the new-address OTP.
- Password reset cannot be completed without a valid, unexpired, unused code.
- Expired, superseded, wrong-purpose, already-used, and brute-forced OTPs are rejected.
- Password reset invalidates relevant sessions.
