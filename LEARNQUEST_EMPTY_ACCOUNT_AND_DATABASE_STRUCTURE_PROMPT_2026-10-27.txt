## PHASE 2 — BRAND-NEW ACCOUNTS MUST START WITH VALID EMPTY LEARNING DATA

This is a central requirement.

**A new, fully onboarded account with no playlists must be a valid account.**

It must not need a playlist, note, focus session, checkpoint, or progress record before it can enter LearnQuest.

Identify the canonical full learning-state schema from the current domain types and store implementation.

Use the existing application's real schema and default values; do not invent fake playlists, video records, XP, progress, notes, analytics, or metrics.

Examples of expected semantics, subject to actual domain types:
- No playlists: an empty playlist collection.
- No active playlist: a null active identifier.
- No checkpoints: an empty checkpoint collection.
- No progress records: an empty progress collection.
- No notes: an empty notes/annotations collection.
- No Focus sessions: an empty sessions collection.
- No goals: an empty goals collection.
- No earned XP: the legitimate initial XP state defined by the application.
- Preferences and metadata: valid defaults consistent with existing application settings.

Use the actual repository types and initialization rules; the list above is illustrative, not permission to make incompatible schemas.

### Distinguish absence from failure

The backend must distinguish these states:

**A. Valid new account:** MongoDB is connected, all required reads completed successfully, and the account has no learning records. Return the canonical empty learning state.

**B. Existing account with data:** Return the complete state with its actual records.

**C. Database unavailable:** Return a genuine availability error.

**D. One or more data queries failed:** Return an explicit error; do not fabricate missing collections.

**E. Malformed or incompatible stored records:** Return a safe, actionable error and preserve all existing records.

**F. Incomplete account onboarding:** Return or route to the onboarding flow instead of treating the account as a complete learning user.

An absent row in a successfully queried, optional collection can mean empty data. A failed query or incomplete response must never silently mean empty data.

Never overwrite valid cloud records with empty defaults merely because the frontend did not receive a complete response.

### Empty-state interface

After a valid new account completes onboarding and cloud initialization succeeds:

- Open the normal LearnQuest dashboard.
- Show an attractive empty-state message that welcomes the user.
- Show a clear "Add your first playlist" or equivalent primary action.
- Make other learning features behave appropriately before a playlist exists.
- Do not show "Your account data is unavailable."
- Do not require the user to manually populate MongoDB or add learning data just to proceed.
- Do not claim that anything is saved until the backend acknowledges the appropriate save.
- Preserve an honest error screen and Retry action for genuine connectivity failures.

Test a brand-new account with zero domain records, then test an account containing real learning records to ensure no data gets lost or replaced.

## PHASE 4 — MAKE THE MONGODB LAYOUT PROFESSIONAL AND EASIER TO INSPECT

The current Atlas `learnquest` database exposes numerous learning-data collections such as:

- `lq_accounts`
- `lq_action_tokens`
- `lq_challenges`
- `lq_data_playlists`
- `lq_data_progress`
- `lq_data_checkpoints`
- `lq_data_sessions`
- `lq_data_goals`
- Other `lq_data_*` collections

The user wants the database to be organized so the top-level view is clean and they can inspect the data belonging to a particular account without navigating a long list of separate learning-domain collection names.

First examine the current schema, data access patterns, database indexes, constraints, collection sizes, and migration behavior. Compare the current layout to a consolidated but logically partitioned user-data collection.

### Target design to evaluate

Prefer an understandable logical organization:

**Account metadata collection** — `lq_accounts`

Contains the account identity and profile fields, Google subject, normalized email and username, onboarding state, password hash, preferences, timestamps, and other appropriate account metadata.

Do not put raw passwords, Google OAuth tokens, session tokens, or email action tokens into account documents.

**Unified learning-data collection** — `lq_user_data`

If compatible with the real repository and benchmarks, consolidate the existing `lq_data_*` collections into a shared collection whose records contain fields comparable to:

- `userId`
- `domain` — the validated learning-data domain, such as playlists, progress, notes, checkpoints, sessions, goals, achievements, settings, or preferences
- `key` — the record/key identifier
- `value` — the validated domain-specific payload
- `version` — if required by the existing version-control model
- `updatedAt`

This is a target design to investigate, not permission to blindly change the database contract. Derive the actual schema from the current code, record types, and indexes before implementing it.

Create suitable compound indexes, including uniqueness on `(userId, domain, key)`, and verify that queries always include authenticated ownership. Add other indexes only when justified by real access patterns.

Keep records small and independently updateable. Do not embed unlimited learning history, every playlist, every session, all video progress, and all notes inside a single account document: MongoDB documents have a 16 MiB size limit, and an oversized document is not a sound storage architecture for growing learning data.

**Operational/security data**

Sessions, OAuth state, email action tokens, migration records, deletion jobs, and version-control records require their own appropriate validation, indexes, and TTL behavior. Do not mix secrets or authentication lifecycles into arbitrary learning-data records.

Use clear namespaces and document the rationale for each remaining collection.

### Important Atlas UI limitation

MongoDB does not have real per-user filesystem folders or collections nested beneath an account document. A database contains collections, and each collection contains documents.

The aim is a clean, logical, scalable layout where learning records are grouped by `userId` and domain and are easy to filter by a selected user. Do not create a separate physical collection for every user, and do not claim that Atlas can display nested per-user collection folders when it cannot.

Provide a short set of Atlas Data Explorer query examples that let the owner filter `lq_user_data` by the selected account's actual `userId` and inspect one learning domain at a time. Use non-secret example identifiers, and never print a real account's sensitive records.

### Indexing and data integrity

Inspect all indexes and confirm:
- Unique normalized usernames and emails where required.
- Multiple pending registrations with null usernames are allowed.
- The intended account identity uniqueness constraints remain enforced.
- Learning-data record uniqueness is appropriately scoped by user and domain.
- All user-facing reads/writes include authenticated user ownership.
- TTL indexes operate only on collections that genuinely require expiry.
- Migration and deletion jobs are retryable and safe.
- No index drop or recreation can silently corrupt or delete user records.

Report the rationale for each compound index and whether the query pattern needs it.

## PHASE 9 — COMPLETE ACCOUNT DELETION AND ZERO-RESIDUAL USER DATA

This phase is mandatory. Inspect the current account-deletion implementation and extend it to guarantee complete, permanent, account-scoped deletion.

### A. Professional, deliberate deletion confirmation

The Account Settings page must provide a clearly labelled **Delete my account** action in a visibly destructive section.

Clicking it must open a confirmation dialog that explains, in plain language, that the operation is permanent and cannot be undone through LearnQuest.

The dialog must require BOTH of the following before deletion can proceed:

1. **Current password:** The user must enter their current password, verified against the account's existing Argon2id password hash on the backend. Never accept a password supplied only for client-side comparison.
2. **Typed confirmation:** Require the user to type exactly:

   `DELETE MY ACCOUNT`

   Trim accidental leading/trailing whitespace, but reject any other phrase or incomplete confirmation.

The dialog must clearly identify the consequences, provide Cancel and Delete permanently actions, and prevent accidental submission.

Require recent reauthentication, with a short server-enforced validity window. If an account legitimately has no password, require fresh Google reauthentication rather than bypassing identity verification.

Do not accept a client-supplied `userId` as authority over which account is deleted. Identify the target exclusively through the authenticated server-side session.

Reject deletion if the password is incorrect, reauthentication has expired, the confirmation phrase is wrong, the session is invalid, or CSRF/origin validation fails. No user data should be deleted on any failed validation.

### B. Delete every record owned by that account

Account deletion must remove all records belonging to that user from every applicable MongoDB collection, including the following where they exist:

- `lq_accounts`
- `lq_sessions`
- `lq_action_tokens`
- `lq_challenges` (including legacy authentication challenges)
- `lq_oauth_states`
- `lq_reset_grants` and other legacy reset-token collections
- `lq_migrations`
- `lq_state_versions`
- `lq_data_*` learning collections, including playlists, progress, metadata, notes/annotations, checkpoints, ranges, modules, goals, Focus sessions, play sessions, queues, achievements, XP, settings, preferences, and statistics
- `lq_user_data` or any consolidated learning-data collection introduced by the database-structure migration
- Account-scoped deletion-job records and any other persisted records associated with the account
- Any additional account-owned collections discovered during repository and database-schema inspection

**Do not assume this list is exhaustive.** Discover every repository, collection, document schema, nested record, and secondary reference that can retain the account's user ID, Google identity, email, username, learning data, session state, migration state, or other personal metadata.

Use the actual current repository schema as the source of truth.

For shared collections containing records from multiple users, delete only records belonging to the authenticated account. Never delete another user's records or shared application configuration.

### C. Cascade through all learning data and metadata

Deleting an account must permanently remove that user's:

- Playlists and imported playlist metadata.
- Video progress and completion history.
- Notes, annotations, and revision history.
- Focus sessions, play sessions, and learning activity history.
- Checkpoints, saved ranges, and modules.
- Goals, challenges, XP records, achievements, and ranking history where account-owned.
- Account preferences, settings, and statistics.
- Migration claims, sync/version metadata, and account-specific recovery records.
- Google-subject linkage and account identity metadata.
- All active sessions, reset links, verification links, action tokens, and authentication state.

Inspect nested arrays, embedded records, secondary indexes, and references to the account's user ID. Remove or correctly clean account-owned references wherever they are persisted outside the primary account collection.

Do not retain a hidden copy of deleted learning content, a recoverable archive, or an orphaned account record in another application collection.

Shared application indexes, collection definitions, code, and settings unrelated to the user may remain. Do not drop a shared database, shared collection, or global index merely because one account is being deleted.

### D. Safe, restartable deletion protocol

Account deletion is irreversible. Implement it as a deliberate, idempotent, resumable process that never reports success after partial deletion.

Inspect whether the existing implementation uses a deletion job or another recovery mechanism. Reuse it if sound; otherwise implement an appropriate deletion protocol.

Requirements:

1. Validate recent reauthentication, current password or alternative account reauthentication, exact confirmation phrase, CSRF, and request origin before starting.
2. Establish a deletion-in-progress state that prevents new sessions, new writes, or conflicting account operations from recreating the user's records during cleanup.
3. Revoke active sessions and ensure previously issued credentials cannot be used to access the account during or after deletion.
4. Delete account-owned data across all discovered collections using the authenticated account's stable identifier.
5. Make every cleanup step safely retryable after an interruption or server restart.
6. Handle concurrent requests and retries without treating incomplete cleanup as successful.
7. Where transactions are genuinely supported, use them where appropriate. If the deployment tier cannot support a multi-document transaction for the complete operation, use a well-designed deletion saga with explicit progress, resumability, and verification rather than assuming atomicity.
8. Verify that no account-owned records remain in any applicable collection.
9. Remove the account's deletion-job metadata itself once deletion has been fully completed and verified.
10. Clear the browser's session cookie, in-memory account state, and account-specific caches, then return the user to the signed-out screen.
11. Do not attempt to save stale client learning state after account deletion. Cancel queued writes and invalidate in-flight loads.
12. Return success only after the server has verified completion. If cleanup is interrupted or incomplete, report that deletion is still pending or has failed, without claiming that the account is gone.

If a process must persist a temporary deletion-job record so interrupted cleanup can resume, retain only the minimum necessary operational metadata while cleanup is incomplete. Ensure the job itself is removed following successful verification. Never permanently retain a completed job that contains the deleted user's identifiers unnecessarily.

Use a deletion lock, tombstone, or equivalent state only as long as the implementation requires it for safe concurrency and retries. Remove that state after successful cleanup.

If deletion fails, keep enough minimal operational information to resume safely, prevent unauthorized access to the account, and explain that deletion has not completed. Do not silently abandon partial deletion.

### E. Post-deletion verification must be exhaustive

Implement a backend verification routine that checks every discovered account-owned collection and relevant secondary reference.

After deletion, verify at minimum that:

- No account document remains for the deleted user.
- No active session remains.
- No password-reset or email-action token remains.
- No OAuth state or pending onboarding record remains.
- No learning collection contains a record owned by the deleted user.
- No migration/version/deletion job retains the user's account-specific metadata after completion.
- No account-owned data is left in a legacy collection after any approved schema migration.
- No other user's data was changed or deleted.
- Old cookies and credentials no longer authenticate the account.
- Repeating the cleanup operation does not recreate data or damage other accounts.

The application must not derive success solely from deleting the document in `lq_accounts`. That is insufficient when other collections still contain personal or learning data.
