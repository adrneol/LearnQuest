## PHASE 1 — INVESTIGATE THE REPORTED EXPIRY PROBLEM

The user received a LearnQuest password-reset email saying the link expires in 10 minutes.

The email was opened approximately 37 minutes after it was received. The user reports being able to open the link and reach the reset flow.

The reset page also displayed:

"The database is currently unavailable. The request was not applied; retry when the service is ready."

Investigate whether the expired token was genuinely accepted for a password change, or whether opening the reset page merely displayed the form before server-side validation.

Do not assume that opening the link proves the token is valid. Equally, do not dismiss the problem without testing the token-consumption endpoint.

Inspect:

- `backend/src/auth/actionTokens.ts`
- `backend/src/routes/auth.ts`
- `backend/src/email/brevo.ts`
- Environment configuration and password-reset constants.
- Token repositories and MongoDB update filters.
- Frontend reset-link parsing and `AuthScreens`/reset components.
- All password-reset API client methods.
- Existing token-expiry, password-reset, and session-revocation tests.

Trace the full path from token creation to link construction, reset-page loading, password submission, token consumption, password-hash update, password-version increment, session revocation, and response rendering.

Use read-only inspection of any available state. Never display existing reset tokens or sensitive account data.

### Required server-side expiration behavior

The server must enforce expiration when consuming the reset token, not merely when rendering the email or reset page.

For every password-reset token:

1. Generate a cryptographically random, high-entropy token.
2. Persist only its HMAC/digest, purpose, account binding, issuance time, expiry time, and other necessary security metadata.
3. Reject tokens that have expired, been consumed, been revoked, or do not match the expected purpose and account.
4. Check expiry against server-side time in UTC.
5. Consume the token atomically, with the actual expiry condition included in the authoritative database operation wherever supported.
6. Prevent concurrent requests from using the same token twice.
7. Update the password and invalidate all previous sessions under the intended atomic or concurrency-safe account-state transition.
8. Invalidate obsolete outstanding email-action tokens after a successful password reset.
9. Reject replay even if a token record remains in MongoDB after expiry or a TTL cleanup delay.
10. Never rely on a MongoDB TTL index alone for security enforcement.

An example of the intended logical condition is that the token is unconsumed, not revoked, has the correct purpose/account binding, and has `expiresAt > now`. Adapt this to the actual repository model rather than blindly copying pseudocode.

If the current implementation already satisfies these properties, demonstrate this with targeted tests and investigate any remaining discrepancy.

### Expiration tests

Use a deterministic fake clock or equivalent test fixture.

Test:
- Token used before expiry: succeeds.
- Token used at or after expiry: fails.
- Token used well after expiry: fails.
- Expired token record still physically present: fails.
- Consumed token replay: fails.
- Concurrent attempts using the same token: at most one succeeds.
- Purpose or account mismatch: fails.
- Password reset rejected because MongoDB is unavailable: no password change or false-success response.
- Successful reset: password hash/password version change correctly and all previous sessions become invalid.
- Unrelated users' accounts and sessions remain unchanged.

Verify token issuance timestamps, expiry calculation, and password reset outcomes. Do not change the existing password policy to solve expiry.

## PHASE 3 — FIX THE RESET LINK'S BASE URL

### Observed defect

The received email contains a reset link beginning with:

`http://localhost:5173/#/reset-password?token=...`

That link is appropriate only for the local development environment. It must never be sent to production users.

The previous audit says the `emailActionUrl` helper constructs the URL using `APP_ORIGIN`. That suggests the localhost URL may come from the local environment rather than being hardcoded into the email template. Verify this directly against the current source and configuration.

### Requirements

1. Search the repository for every hardcoded localhost URL, public frontend domain, and password-reset URL constructor.
2. Ensure all password-reset, email-change, and other email-action links use the configured public application origin appropriate to the active environment.
3. Use the existing `APP_ORIGIN` configuration variable where appropriate rather than scattering production URLs throughout source code.
4. Do not derive the public origin from an untrusted request `Host` or forwarded-host header.
5. Do not allow an arbitrary client-supplied origin to control a security-sensitive action URL.
6. The production configuration must use the deployed frontend origin:

   `https://learn-quest-one.vercel.app`

7. The production configuration must reject missing, invalid, or localhost origins. It must not silently generate a production email that points to localhost.
8. Local development may use `http://localhost:5173` only in a deliberately configured development environment.
9. Validate URL syntax, permitted schemes, and origin expectations at configuration load time.
10. Keep reset tokens in the URL fragment if that is the existing secure flow, preserving explicit POST submission and avoiding automatic token consumption by GET requests.
11. Ensure the actual hash-router reset route can parse the link correctly.
12. Keep the configured expiry and origin independent: changing the origin must not change token validity.

The production public origin belongs in the backend's private environment configuration, such as Render's `APP_ORIGIN`. It is not a secret itself, but it must be configured explicitly and validated. Do not place API keys or other backend secrets in the Vercel frontend bundle.

Inspect `render.yaml` and the actual deployment instructions. Keep configuration changes consistent with the current deployment model. If a static value in deployment configuration is necessary to set the environment variable, it must not become a separate hardcoded URL inside business logic.

Do not edit production dashboard settings automatically.

### URL construction tests

Add tests for:
- Local development with a valid localhost origin.
- Production using `https://learn-quest-one.vercel.app`.
- Production configuration missing `APP_ORIGIN`.
- Production origin set to localhost.
- Invalid URL and unapproved scheme.
- URL containing an unexpected path, query, or fragment.
- Reset link preserving the correct hash route and token handling.
- Email template using the actual configured origin.
- Preventing untrusted request headers from overriding the configured origin.
- Email-change links using the appropriate configured origin as well.

No test should print a live reset token or secret.

If the link has expired, provide a clean, professional expired-link state with an obvious request-new-link action.

Ensure the frontend does not confuse:
- Page opening.
- Token validation.
- Form submission.
- Password change committed.
- Session revocation completed.

Treat them as separate states.
