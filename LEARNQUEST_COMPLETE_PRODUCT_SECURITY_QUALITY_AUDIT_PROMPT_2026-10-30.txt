# PART II — CRITICAL AUTHENTICATION AND SESSION AUDIT

## 3. Investigate the actual logout synchronization bug

The user reports two reproducible behaviors:

**Case A — Sign out from one browser**

The user clicks Sign Out in one tab. Another tab belonging to the same browser profile continues displaying the authenticated application until manually refreshed.

**Case B — Sign out from all devices**

The user selects the all-devices logout option. Another browser/device continues displaying the authenticated application until that device is refreshed.

Treat these as two separate synchronization problems. Investigate both independently.

Do not confuse:
- Cookie deletion.
- Server-side session revocation.
- Frontend authentication-state clearing.
- Cross-tab synchronization.
- Cross-device revocation propagation.

### 3.1 Single-browser, multi-tab investigation

Trace the entire logout lifecycle:

1. User clicks Sign Out.
2. Frontend sends the sign-out request.
3. Backend validates the session.
4. Backend revokes the correct server-side session.
5. Backend clears the session cookie.
6. Frontend clears its authentication state.
7. Other same-origin tabs receive or fail to receive the logout event.
8. Other tabs discard authenticated screens, cached user data, pending requests, and stale in-memory state.

Investigate:
- Is `BroadcastChannel` implemented?
- Is a `storage` event used?
- Is localStorage used as a cross-tab signal?
- Is the event sent before or after server revocation?
- Does another tab actually subscribe to it?
- Does a tab only check authentication during initialization?
- Can cached React state continue displaying private content after revocation?
- Can an unfinished API request rehydrate the old account?
- Can an old session-status request overwrite the signed-out state?
- Does an inactive/background tab process the event correctly when reactivated?
- Does the sign-out event contain a token, cookie, session ID, or other sensitive data?

Evaluate the actual implementation, not just the presence of a BroadcastChannel or storage event.

### Required desired behavior

For logout from one browser:

- All tabs sharing that browser profile must transition to signed-out UI promptly.
- The current session must be revoked on the server.
- All tabs must clear stale private UI and pending user-data state.
- New protected API operations must fail.
- Late asynchronous responses must not restore authentication.
- The user must be able to sign in again normally.

Make it clear whether the implementation provides immediate visual synchronization, authoritative server revocation, or both.

### 3.2 All-devices logout investigation

Trace the server-side implementation.

Determine:
- Does logout-all revoke every active session belonging to the account?
- Does it exclude the current session accidentally?
- Does it delete sessions or mark them revoked?
- Does the session validator check revocation on every protected request?
- Are password-version changes used?
- Is session status cached in the backend or frontend?
- Are session revocations immediately visible across multiple Render processes?
- Can an old session be recreated because of a refresh or race?
- Do cookies get cleared on the initiating device?
- Do all other devices eventually receive a server rejection?
- Are long-lived pages or players still allowed to display private account data after revocation?
- Do background data synchronization operations stop?
- Is there a session-status endpoint or heartbeat?
- Is there an existing cross-device event channel?

### Required desired behavior

When the user chooses logout from all devices:

1. The backend revokes all active sessions for that account.
2. The initiating browser signs out.
3. Other devices stop being authorized immediately at the server level.
4. Other devices display a signed-out state promptly, without requiring a manual page refresh.
5. In-flight API operations cannot silently restore the old account.
6. Re-authentication requires fresh login.
7. The user's learning data remains in MongoDB; logout must never delete learning data.

### Important technical distinction

A remote browser cannot always receive an instantaneous visual logout if it is idle, disconnected, or its device is asleep.

Evaluate suitable mechanisms, such as:
- Cross-tab `BroadcastChannel` synchronization.
- Server-authoritative session validation.
- Periodic lightweight session-status checks.
- Server-sent events or WebSocket notifications where justified.
- Visibility/focus-triggered revalidation.
- Revocation/version checks on every protected request.

Compare options on reliability, cost, battery/network use, implementation complexity, Render infrastructure constraints, and security.

Recommend a practical architecture for LearnQuest. Do not implement it.

## 2. Recommended formula investigation — Focus, Efficiency, and Arena

I want actionable mathematical recommendations, not merely statements that an algorithm is good or bad.

For every existing formula:
- Locate its actual implementation.
- Identify every input and its source.
- Explain the units and mathematical meaning.
- Check edge cases and possible manipulation.
- Compare actual implementation with the candidate design below.
- Show worked numerical examples.
- Recommend a final formula only after inspecting the real data model and product behaviour.

Never invent input signals that the application does not collect.

### 2.1 Efficiency: distinguish learning throughput from learning quality

Investigate whether the current efficiency calculation is mathematically meaningful and whether its name accurately describes what it measures.

A candidate baseline is:

`Learning Throughput (%) = 100 × Total Unique Content Seconds / Total Qualified Focus Seconds`

Where:

- `Unique Content Seconds` means genuinely unique learning content completed, with duplicate watching and repeated progress events handled correctly.
- `Qualified Focus Seconds` means valid focus-session time after pauses, idle periods, invalid intervals, and overlapping sessions have been handled.
- Period-level calculation should use the ratio of totals, not the unweighted arithmetic mean of daily percentages.

For example, compare:

`100 × (U1 + U2 + ... + Un) / (F1 + F2 + ... + Fn)`

against:

`(DailyEfficiency1 + DailyEfficiency2 + ... + DailyEfficiencyN) / n`

Explain why the two calculations can produce different results, and which one is justified for LearnQuest.

**Important:** This is a content-throughput measure, not proof of comprehension, retention, intelligence, or learning quality.

The result can exceed 100% because content duration and elapsed focus time are not necessarily the same unit of activity, especially with playback speed changes. Do not silently cap, distort, or misrepresent the raw value.

Investigate whether playback speed and segment-level watch telemetry are reliably available. If they are, evaluate a playback-adjusted alternative:

`Expected Playback Time = Σ (Unique Watched Segment Content Seconds / Segment Playback Speed)`

`Playback-Adjusted Pace (%) = 100 × Expected Playback Time / Qualified Focus Seconds`

Validate whether the inputs genuinely represent watched segments rather than skipped or merely marked-complete content. Do not use this adjusted formula if the required telemetry is unavailable or unreliable.

Recommend whether the existing metric should remain named Efficiency, be renamed Learning Pace or Learning Throughput, or be separated into multiple metrics.

Do not manufacture a composite efficiency score without a defensible reason.

### 2.2 Focus: recommended accounting model

Investigate the current focus timer from the perspective of data correctness and user trust.

A candidate accounting model is:

`Qualified Focus Time = Union(Valid Active Intervals) - Union(Paused Intervals ∪ Disqualified Idle Intervals)`

The implementation must avoid counting overlapping intervals more than once, including where multiple tabs or devices are involved.

Investigate:
- Start, pause, resume, stop, and reset operations.
- Browser refresh, tab closing, crashes, and recovery.
- Browser backgrounding, visibility changes, sleep, and device wake-up.
- Timer throttling and delayed callbacks.
- Idle detection and false idle detection.
- Duplicate sessions and simultaneous sessions.
- Multi-tab and multi-device overlap.
- Clock changes, timezones, midnight boundaries, and daylight-saving transitions where applicable.
- Periodic persistence and data-loss windows.
- Session ownership, concurrent writes, and race conditions.
- Whether users can accidentally accumulate focus time without actively studying.

Do not treat page visibility as proof of attention. It is only a contextual signal.

Recommend a reliable architecture for tracking and persisting focus intervals. Define which events are authoritative, how interruptions are reconciled, and how corrupted or incomplete sessions are handled.

Also identify whether Focus should display only trustworthy quantities such as focused minutes, session duration, active days, and trends, rather than suggesting that the application can measure a user's actual concentration.

### 2.3 Arena: propose a mathematically defensible new simulation

Investigate the entire current Arena implementation. Do not simply patch individual ranking defects.

The proposed redesign should separate:

1. The user's actual learning progress.
2. The ranking/scoring system.
3. Simulated competitor generation.
4. Challenge difficulty.
5. User-configurable Arena preferences.
6. Ranking presentation and explanations.

A candidate baseline score for a playlist-based competition is:

`P = min(Unique Completed Content Seconds / Total Eligible Playlist Seconds, 1)`

`C = min(Qualifying Active Days / Elapsed Competition Days, 1)`

`Arena Score = 100 × (0.85 × P + 0.15 × C)`

This is a **provisional candidate**, not a required final formula.

Investigate whether the 85/15 weighting is appropriate. Compare alternative approaches, run sensitivity analysis, and explain the trade-offs. Do not present arbitrary weights as scientifically established.

Define qualifying active days carefully. Do not allow a user to improve a ranking merely by leaving a focus timer running. Explain what minimum valid activity and progress evidence would be required.

The design must consider:
- Progress across short and long playlists.
- Repeated viewing and duplicate progress.
- Skipping, seeking, playback-speed changes, and partial completion.
- New users and late competition entry.
- Burst learning versus consistent learning.
- Different competition windows.
- Missing, incomplete, imported, and reset data.
- Timezone-safe daily aggregation.
- Ties and deterministic tie-breaking.
- Score bounds and invalid inputs.
- Competitor realism and distribution.
- Reproducibility across refreshes and devices.

### Simulated competitors

All competitors and the user should be evaluated using the same defined scoring rules and comparable competition windows.

A simulation should be deterministic for the same inputs, with an explicit algorithm version and stable seed. Competitor progress must be bounded by playlist duration, monotonic where appropriate, and consistent with the selected difficulty.

Clearly distinguish simulated opponents from real users. Do not create the impression that simulated rankings are real-world leaderboard results.

Recommend a realistic opponent-generation model rather than arbitrary random daily percentages. Explain how competitor learning trajectories, activity patterns, completion rates, and difficulty distributions should be generated and validated.

### Recommended user-facing Arena options

Evaluate an interface that lets users control the simulation experience, for example:

- Competition intensity: Relaxed, Standard, or Competitive.
- Number of simulated competitors.
- Competition period or challenge window.
- Whether to show competitor progress and ranking explanations.
- Restart or generate a new simulation cohort, where appropriate.

Crucial distinction: preferences may adjust the simulation cohort or difficulty, but must not secretly change the user's underlying learning progress or manipulate an official score.

Recommend a clear separation between personal learning statistics, simulated Arena results, and any future real-user leaderboard.

Provide the proposed UI structure, interaction behaviour, settings persistence requirements, empty states, explanations, and accessibility considerations.

Include complete worked examples of the proposed ranking formula and explain how it handles ties, incomplete data, and new users.
