# 3. P0 — DIAGNOSE LOCAL VS PRODUCTION GOOGLE ACCOUNT DUPLICATE

## 3.1 Establish whether the local and production databases are actually the same

The fact that a Gmail address exists in production but can be used in local development does NOT by itself prove duplicate-email validation is broken. Local and production commonly use different MongoDB databases or clusters; unique indexes are scoped to a database/collection, not shared between separate deployments.

Prove the topology without exposing secrets:

- Inspect the backend's configuration-loading code and actual runtime Mongo client/database selection.
- Never print, read into logs, copy, or expose `.env`, MongoDB URI, passwords, hostnames, credentials, or private account data.
- If a safe diagnostic is needed, report only a non-sensitive database name or an irreversible short fingerprint generated in memory; do not print the connection URI or cluster hostname.
- Do not query production for this Gmail address and do not use production credentials. Do not attempt a live production sign-up.
- State clearly whether the local app points to a separate local database, a separate database on the same cluster, or the same database. If production topology cannot be verified from authorized evidence, say so.

Interpretation:

- If local and production use different databases, accepting the same email locally can be expected and does not imply a production duplicate bug.
- If both use the same database, investigate the normalization, lookup, unique index, race handling and Google subject matching as a real defect.
- Never modify production records to test this.

## 3.2 Audit uniqueness and account identity

Inspect current account creation, Google OAuth registration/login intents, account lookup, database indexes, email normalization, and unique-key handling.

Verify:

- All account creation paths use one canonical email normalization function.
- The intended normalized email has a database-enforced unique index, not only an application pre-check.
- Google `sub` has the correct uniqueness guarantee (sparse/partial semantics appropriate to the current account model).
- Concurrent registrations with the same normalized email cannot create two accounts.
- Mongo duplicate-key errors are handled safely and consistently.
- Lookup uses the stable Google `sub` as the primary identity when linked; email is a secondary uniqueness/association signal.
- Case/whitespace variants cannot bypass uniqueness.
- Do not strip Gmail dots or plus-tags or apply provider-specific alias rewriting unless the product has explicitly adopted and tested that identity policy. Do not merge addresses based on assumptions.
- Keep account scoping and existing session, CSRF, OAuth state, browser binding, rate limiting and non-enumeration protections.

Add unit, backend integration and concurrency tests for uniqueness, existing identities, normalized variants, duplicate-key races and account isolation.

## 3.3 Desired sign-in/sign-up experience

The owner wants a simple experience:

- If a user starts from Sign Up with a Google identity that is already linked to a LearnQuest account, authenticate/sign in to that existing account rather than creating another account or showing a blunt “email already exists” error.
- If a user starts from Sign In and the authenticated Google identity is not linked to any LearnQuest account, offer a clear “Create your LearnQuest account” / sign-up path.
- If there is no existing account and the user confirms account creation, proceed through the existing Google onboarding flow.
- If the verified Google email matches an existing account but its Google `sub` is different or not linked, DO NOT silently attach it or log the user into that account based only on matching email. Require proof of control through that account's existing sign-in method and an explicit secure linking flow with recent authentication, or block linking with clear next steps.
- Never automatically merge two accounts or move learning data because email strings match.
- If a stable Google `sub` is already linked, use that identity to sign the user into the existing account, irrespective of which screen they started from.
- Avoid disclosing account existence to unauthenticated callers through an unprotected email lookup/preflight endpoint. Rate-limit identity operations and use generic responses where needed. After a verified Google identity is established, give the legitimate user actionable next steps.

Implement a cohesive Google-first identity resolution flow rather than two registration/login paths that can disagree. Keep account creation explicit. Preserve existing account data and OTP functionality unrelated to this flow.

Required tests:

1. Existing linked Google `sub` from Sign Up -> signs in existing account; no new account.
2. Existing linked Google `sub` from Sign In -> signs in existing account.
3. New verified Google identity with no matching account -> offers/starts onboarding only after explicit user action.
4. Email matching an existing account but different/unlinked `sub` -> no auto-link, no login takeover, safe proof/link path required.
5. Same normalized email concurrent requests -> at most one account.
6. Case/whitespace normalization cannot bypass uniqueness.
7. Duplicate-key race is handled without a second account.
8. Existing OTP and password flows remain functional.
9. No account enumeration regression, no secret or email-token leakage.
10. Local and production database separation is documented accurately.

# 4. P0 — LEGACY TO UNIFIED ZERO-LOSS MIGRATION

The owner intends to migrate to Unified after the engineering and staging work is complete. Treat data preservation as the highest priority. No collection/domain or record may be silently lost.

## 4.1 Inventory and contract proof

Inspect the actual Legacy and Unified adapters, migration scripts, indexes, collection names, key schemas, account deletion behavior and import/export paths.

The current logical domains are expected to include these 20 entries; verify the source of truth and do not omit or rename any:

`playlists`, `meta`, `progress`, `ranges`, `checkpoints`, `modules`, `sessions`, `goals`, `xp`, `achievements`, `segments`, `playSessions`, `queue`, `flexGoals`, `challenge`, `challengeEnabled`, `rankHistory`, `settings`, `prefs`, `activeId`.

For each domain document:

- Legacy physical collection and logical key mapping.
- Unified record shape and indexes.
- Stable identity and ordering semantics.
- Empty-domain behavior.
- Validation and size limits.
- User ownership and deletion scope.
- Import/export/restore behavior.
- Whether append operations and optimistic versions behave identically.

Prove both adapters satisfy the same repository contract for every domain. A successful migration must preserve every logical record, its stable identity, ordering where meaningful, timestamps/versions where meaningful, user ownership, and all required metadata. Empty domains must remain represented as empty logical domains after the switch.

Do not interpret “Unified uses one physical collection” as permission to drop logical domain coverage. The user explicitly requires no collection/domain loss and no record loss.

## 4.2 Migration protocol — no moving target snapshot

Design a cross-process, server-authoritative write-freeze or an equivalently strong change-capture protocol. An in-memory flag is not sufficient for multi-instance Render deployments.

The protocol must:

1. Acquire a durable migration fence visible to every backend process.
2. Prevent new learning-data mutations during the final snapshot window (including PUT, append, import, local-data migration, playlist/learning mutations, Focus/XP writes, and any other write path identified by source inspection).
3. Drain or safely account for in-flight writes before taking the final source snapshot.
4. Make clients show an explicit maintenance/read-only state while preserving pending local edits; do not discard queued user changes.
5. Record a migration ID, schema version, fence generation, start/end times, source version and domain inventory.
6. Copy all users and all 20 logical domains to Unified using stable identities and idempotent operations.
7. Compute canonical per-user/per-domain counts and checksums before and after copy.
8. Re-read/verify the source snapshot while the fence remains active. Any source mutation, missing record, extra unexpected record, checksum mismatch, duplicate, invalid record or unresolved conflict must fail the migration closed.
9. Reconcile destination-only records explicitly. Never silently delete or overwrite them.
10. Make interrupted runs resumable and idempotent, with a durable per-account/per-domain progress journal.
11. Keep Legacy data unchanged throughout migration and cutover.
12. Switch the application to Unified only after every required parity gate succeeds and an explicit owner-approved cutover operation is issued.
13. Release the write fence only after the selected storage mode is confirmed and a read/write smoke test passes.

No silent fallback from Unified to Legacy. A mode mismatch or missing Unified state must fail clearly rather than show an empty account or mix two sources of truth.

## 4.3 Reverse migration and rollback

Implement a tested reverse path before production cutover.

A rollback must preserve every write accepted after Unified becomes active. It is not enough to leave old Legacy collections untouched and switch the environment variable back.

Use a controlled freeze again, copy/reconcile all Unified-era writes into Legacy, verify all domains and checksums, confirm no conflicts or missing records, and only then permit switching the active mode back. If a reverse copy cannot prove parity, keep the system fenced/read-only and block rollback rather than lose data.

Do not permanently dual-write both adapters as an unreviewed shortcut or introduce two authoritative sources. If a temporary change log/outbox is selected, document why and prove replay/idempotency.

## 4.4 Backup and restore proof

Write a documented operator runbook for a full database backup and restore rehearsal.

- Use an isolated staging/test database only.
- Never print credentials or URIs.
- Restore the backup into a separate empty database.
- Verify logical domain counts and canonical checksums for all 20 domains.
- Include accounts and required account metadata in the backup plan, while ensuring no real production PII is copied to staging without explicit authorization and a privacy-safe plan.
- A CLI flag or operator checkbox saying “backup confirmed” is not proof. Require a recorded restore-verification artifact.

## 4.5 Staging rehearsal and migration gates

Create representative synthetic fixtures including empty domains, large histories, duplicate identities, conflicting destination data, destination-only data, malformed records, account deletion races, concurrent writes, and partial interruption.

Test at least:

- Legacy repository contract for all 20 domains.
- Unified repository contract for all 20 domains.
- Cross-adapter read/write parity.
- Exact count and checksum parity.
- No fallback when Unified is selected and empty.
- Dry run produces zero writes.
- Apply copies all domains.
- Re-run is idempotent.
- Source and destination conflicts block safely.
- Duplicate source/destination records block safely.
- Destination-only records are preserved pending explicit reconciliation.
- Source mutation during copy is detected and blocks completion.
- Interrupted copy resumes without loss or duplication.
- Account deletion cannot resurrect records.
- Import/export and restore work in both modes.
- Large account/transaction/payload limits are measured.
- Freeze blocks every identified mutation route and drains in-flight writes.
- Reverse migration preserves Unified-era writes.
- Backup restore reproduces counts/checksums.

Use an actual isolated MongoDB replica set for transaction/migration integration tests if required. In-memory tests alone are not evidence of production transaction behavior. Do not use production credentials.

## 4.6 Cutover decision gate

The owner intends to migrate production after the implementation is complete. Therefore, do not stop at vague “migration not ready” notes: implement the missing code, tests, runbooks and staging rehearsal as far as possible.

However, do NOT switch production storage or run production migration automatically. Before the live operation, produce a separate cutover checklist that names:

- Exact target database and environment, described without exposing secrets.
- The exact 20-domain source/destination inventory.
- Backup and restore proof.
- Staging parity artifact.
- Freeze/drain proof.
- Destination-only/conflict reconciliation approvals.
- Reverse-migration rehearsal result.
- Rollback decision and expected maintenance window.
- Final source/target counts and checksums.
- The exact operator command/environment change to be used.

Stop and request the owner's explicit final authorization for the production cutover. Do not infer production authorization from permission to implement or test the migration system.

Keep `LQ_USER_DATA_STORE=legacy` as production default until that approval and all gates pass. Never drop or retire Legacy collections in this phase. Retention/retirement needs a separate post-cutover observation period and explicit approval.
