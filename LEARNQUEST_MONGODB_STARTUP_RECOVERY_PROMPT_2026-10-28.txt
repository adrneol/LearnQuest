## PHASE 3 — IMPLEMENT A SAFE, RESILIENT STARTUP LIFECYCLE

The app currently opens its HTTP listener even when MongoDB is unavailable. This allows the frontend and backend to start, but data operations must remain unavailable until database readiness is established.

Inspect the entire lifecycle:
- Initial connection and ping.
- Cached MongoDB connection promises.
- Index initialization.
- Database store initialization.
- Health and readiness endpoints.
- Request-time connection retries.
- Server shutdown and MongoDB client cleanup.
- Existing pending-account-deletion recovery.

Fix any demonstrated defects in the current lifecycle.

### Required behavior

1. Distinguish HTTP liveness from MongoDB readiness. A running HTTP process must not claim that database operations are ready when the ping fails.
2. Keep authentication and data endpoints fail-closed when MongoDB is unavailable.
3. Preserve sanitized failure messages and avoid exposing driver internals or secrets.
4. Ensure rejected connection promises are not cached permanently.
5. Use bounded, sensible connection timeouts.
6. Avoid an aggressive retry loop that hammers Atlas or floods logs.
7. If automatic reconnection is implemented, use controlled exponential backoff with a reasonable maximum interval, clear cancellation, and clean shutdown handling.
8. Once connectivity returns, establish readiness only after the required connection checks and schema/index prerequisites succeed.
9. Ensure a recovered connection cannot cause partially initialized stores, inconsistent readiness, duplicate startup tasks, or concurrent initialization races.
10. Do not silently switch to local-only storage or fabricate an empty account when the database is unavailable.

### Destructive startup work

The previous report identifies a startup path that may resume pending account-deletion jobs.

Do not introduce an automatic retry path that blindly triggers account deletion, migration, or legacy retirement.

Inspect and preserve the existing deletion safety guarantees. Review how startup recovery is authorized and how unexpected deletion jobs can be discovered before enabling a maintenance path.

Separate connection recovery from destructive maintenance. If the database reconnects, ordinary reads and writes must not depend on running an unrelated destructive migration or deleting accounts.

Any change to the automatic deletion-recovery policy must be justified, tested, and documented. Never skip a legitimate deletion record silently or claim that its data was deleted when it remains.
