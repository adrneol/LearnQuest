## 3. Data integrity: fix all High-severity findings

### LQ-001 — Progress identity follows the wrong video after playlist changes

Previous finding: progress is keyed by playlist position, such as `playlistId::position`, rather than a reliable video identity.

Inspect `frontend/src/domain/progress/progress.ts`, `frontend/src/app/store.tsx`, playlist snapshot handling, XP/achievement deduplication, and every downstream consumer.

Implement a stable identity and migration strategy that:

- Prevents a completion from silently transferring to a different video after reordering, insertion, deletion, or refresh.
- Handles duplicate occurrences of the same YouTube video in one playlist intentionally.
- Reconciles existing progress with stored `videoId` values.
- Flags mismatches for review rather than transferring completion blindly.
- Preserves user-authored annotations and historical records.
- Keeps Dashboard, Library, Reports, Checkpoints, Goals, Analytics, Arena, Revision, and XP consistent.
- Remains backwards-compatible with existing IndexedDB data and older backups.

Do not simply replace every position key with a video ID and discard the distinction between duplicate occurrences.

Add tests for reordered playlists, insertion, deletion, duplicate video IDs, legacy records, refresh, and migration.

### LQ-002 — Backup restore is unvalidated and non-atomic

Previous finding: restore accepts arbitrary JSON, partially merges keys, ignores important validation, and can leave mixed old/new state.

Implement a versioned backup schema and a genuine restore process.

Requirements:

- Validate the complete backup and all nested data before altering state.
- Validate key types, timestamps, IDs, cross-record references, and collection limits.
- Reject unsupported or malformed schemas with clear errors.
- Make restore semantics explicit and consistent with UI wording.
- Do not silently retain omitted keys when the operation promises a full restore.
- Stage the restored state, then apply it atomically.
- Prefer a single IndexedDB transaction or an equivalent all-or-nothing persistence boundary.
- Update React state only after the restore has committed successfully.
- Preserve all state if validation or persistence fails.
- Offer a safe pre-restore backup/recovery path.
- Provide clear error information without exposing sensitive content.

Test complete backups, missing fields, malformed timestamps, invalid nested records, unsupported versions, partially valid data, storage failures, and backwards-compatible migration.

Do not test by replacing my actual browser database.

### LQ-003 — Focus session timestamps are synthetic

Previous finding: session start time is reconstructed from active seconds, which loses real pauses and can misattribute activity across midnight.

Audit the Focus timer from start through pause, resume, finish, persistence, reload, and history/analytics calculations.

Preserve actual wall-clock start and finish times. Represent active and paused intervals sufficiently to make duration and day-attribution behavior accurate.

Ensure:

- Active duration excludes pauses.
- Wall-clock duration includes elapsed pauses.
- Start and finish timestamps remain real timestamps.
- Repeated clicks cannot double-finish a session or award XP repeatedly.
- Tab switching, browser visibility changes, reloads, and unmounting do not create phantom time.
- Cross-midnight attribution is consistent.
- Invalid timer state cannot corrupt saved sessions.
- Historical sessions can still be displayed after a compatible migration.

Add deterministic fake-clock tests for start, pause, resume, repeated pause/resume, finish, cross-midnight work, invalid state, reload/recovery, and duplicate completion.

### LQ-004 — Manual and verified playback evidence are conflated

Previous finding: manual segments can contribute to verified coverage, and verified records can receive manual-completion labels.

Enforce evidence provenance throughout the domain, store, player, history, analytics, efficiency, goals, Arena, and exports.

Only genuine player-observed evidence may contribute to verified completion. Manual entries must remain clearly identified as manual; verified completion must not be inferred from self-reported time.

Do not destroy legitimate manual history. Distinguish verified metrics from manual or estimated metrics wherever necessary.

Ensure the threshold calculation remains correct, partial coverage remains partial, and labels agree with stored evidence.

Test mixed evidence, overlapping segments, repeated playback, seeking, completion thresholds, manual-only history, and verified-record labels.

### LQ-005 — Unmarking completion destroys annotations

Previous finding: marking or unmarking replaces/deletes the whole progress record and loses notes, confidence, revision dates, exercise flags, questions, and other learning metadata.

Change completion actions to patch only the relevant completion fields.

Preserve all unrelated annotations and ensure the result survives persistence and reload. Handle any dependent XP/achievement reversal or idempotency consistently with the existing rules; never silently grant duplicate rewards.

Test every annotation field across mark, unmark, reload, and re-mark operations.

### LQ-006 — Invalid session length can crash the application

Previous finding: a session length of zero can reach a calculation that throws and blank the app.

Add centralized validation at input boundaries, state updates, and persistence restoration.

Reject or normalize zero, negative, non-finite, empty, and unreasonable values appropriately. Provide inline feedback and prevent invalid settings from being persisted.

Add an application-level error boundary with a usable recovery state. A render failure must not leave an unexplained blank screen.

Test invalid and boundary values in Settings, Reports, Focus, Library, and any other component using session planning. Verify the app remains usable after failure.

### LQ-007 — Imported playlist snapshots accept invalid structure

Previous finding: non-contiguous positions and `NaN` reported counts can pass validation.

Validate snapshot schema, entry positions, IDs, duplicate video IDs, duration shapes, finite non-negative counts, timestamps, and the maximum supported size.

Reject invalid snapshots or normalize incomplete information explicitly. Do not invent missing videos or durations. Incomplete metadata must remain visibly incomplete.

Test gaps, duplicate positions, duplicate video IDs, NaN/infinite counts, invalid timestamps, empty playlists, and oversized snapshots.

## 6. Numeric fields: eliminate unwanted leading zeros

Across the application, inspect numeric inputs and controlled-value formatting. The user has observed inputs displaying values such as `019` instead of `19` across several areas.

Find the actual cause in the current implementation instead of applying a superficial string replacement.

Normalize numeric display and saved values consistently for genuine numeric fields, including values for session length, checkpoints, ranges, goals, Focus settings, positions, durations, thresholds, or other numeric controls discovered in the repository.

- Support valid integer or decimal input as appropriate for each field.
- Maintain correct min/max constraints, step rules, and validation messages.
- Avoid updating a controlled field so aggressively on every keystroke that typing becomes impossible.

- Preserve intentional string identifiers, date/time formats, IDs, and any other values where leading zeros are semantically meaningful.

- Never allow invalid numeric state to reach domain calculations or persistence.
- Keep the UI formatting consistent without breaking accessibility or cursor position.

Add reusable helpers/components only where they provide a clear improvement. Avoid unnecessary abstraction.

Add tests covering leading zeros, empty values, zero, negative values where invalid, decimals, min/max values, editing state, blur/commit behavior, and persistence. Verify the affected fields through the UI rather than checking only a helper function.
