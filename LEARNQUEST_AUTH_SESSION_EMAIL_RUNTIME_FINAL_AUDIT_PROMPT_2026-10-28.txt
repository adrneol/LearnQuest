## PHASE 3 — DEEP SESSION AND COOKIE SECURITY AUDIT

Audit the real authentication lifecycle end to end. Fix any demonstrated defects found within this scope.

### A. Cookie properties and topology

Inspect how session cookies are issued, renewed, cleared, and validated in local development and production.

Verify:
- `HttpOnly` is enabled.
- `Secure` is enabled in production.
- `SameSite` is correct for the actual Vercel/Render request topology.
- The cookie's path, domain, expiry, and other attributes are consistent when setting and clearing it.
- Credentialed CORS uses explicit trusted origins, never an unrestricted origin with credentials.
- CSRF protection is enforced for state-changing operations.
- Proxy and forwarded-header handling is consistent with the actual trusted deployment topology.
- Session expiry is enforced server-side, including idle timeout and absolute lifetime.
- Password, OAuth, and session secrets are never stored in browser storage.
- Learning records, notes, playlists, progress, and analytics are never placed in the session cookie.
- Authentication state is not trusted solely from client-side flags.
- A stale cookie cannot revive a revoked session.

The earlier audit identified a deployment topology in which the Vercel frontend and Render backend use different site domains. Verify whether the application uses a same-origin `/api` proxy or direct cross-origin requests.

Do not blindly change cookies to `SameSite=None`, disable `Secure`, broaden CORS, or add a permissive domain. Choose a secure configuration appropriate to the actual request architecture. If the current topology makes the intended session behavior impossible, fix the architecture or provide a precise owner-side deployment requirement.

### B. Login and session lifecycle

Verify and fix as needed:

- Session rotation after successful authentication.
- Protection against session fixation.
- Correct cookie issuance on password and Google sign-in.
- Safe behavior for failed login attempts.
- Proper session revocation at logout.
- Reliable session lookup and revocation in MongoDB.
- Prevention of expired sessions being treated as active.
- Revocation of old sessions after password reset.
- Correct invalidation of all previously issued sessions after account deletion.
- No persistence of old browser state after the server rejects a session.
- No user-data writes after sign-out or account deletion.
- No race that lets a stale asynchronous response restore authentication.
- Correct account isolation on every protected endpoint.
- No client-supplied `userId` being trusted as the authenticated identity.

### C. Cross-tab behavior

The required behavior is:

- Opening a second tab in the same browser profile should reuse a still-valid server-side session.
- Signing out in one tab should immediately synchronize the UI of other same-origin tabs.
- The synchronization event must not include tokens, passwords, personal data, or session identifiers.
- The server must remain authoritative; a broadcast is never proof of valid authentication.
- Old or pending API responses must not restore authenticated UI after logout.
- A password reset must invalidate sessions on every device, not merely close the current tab.
- The browser cookie must be cleared with the correct attributes.
- Recovery and public authentication pages must not inherit irrelevant expired-session warnings.

Add regression tests using independent tabs or the existing cross-tab test harness where available.

Do not claim full browser-level verification if only mocked unit tests were run. Clearly report which scenarios were tested in a real browser.

## PHASE 4 — PASSWORD RESET, TOKEN SAFETY, AND ACCOUNT RECOVERY

Report 16 describes a strong server-side reset-token design. Verify that it remains correct.

Required behavior:

- High-entropy cryptographically random action tokens.
- Digest/HMAC storage rather than raw reset tokens.
- Purpose and account binding.
- Server-enforced expiration.
- Atomic single-use token consumption.
- Rejection of expired, malformed, consumed, and replayed tokens.
- No token consumption on GET.
- No false success if MongoDB is unavailable.
- Password hash updates only after a successful validated request.
- Session revocation after successful reset.
- Invalidation of outstanding reset grants/actions as required.
- No sensitive tokens in logs, analytics, browser storage, or exception messages.

Ensure the reset-success screen appears only after the actual password-change operation succeeds and the backend confirms its required state transition.

Do not claim every external session was revoked just because the frontend navigated to the success screen; verify server-side revocation and tests.

Search all active security-sensitive code paths for `Math.random`. Any use for an OTP, reset token, verification code, session token, or security challenge must be replaced with appropriate Node.js cryptographic randomness. Preserve ordinary non-security random uses when harmless.

For any remaining numeric OTP flow that is deliberately part of the product:
- Use `crypto.randomInt` or an equivalent cryptographically secure generator.
- Use server-enforced expiry, attempt limits, cooldown, and atomic single-use consumption.
- Bind the code to the account and intended purpose.
- Store a secure digest/HMAC rather than the raw code where appropriate.
- Invalidate old codes on successful verification and resend.
- Never log or expose codes.

Password reset should continue using the existing single-use email-link flow rather than adding an unnecessary numeric OTP field.

7. Failed provider requests must be diagnosed without logging credentials or action tokens.
8. Provider acceptance must not be described as confirmed delivery.

11. Password reset and email-change actions must use the correct purpose and expiry policy.
12. The sender name and design should look professional and contain concise instructions, expiry, and ignore-if-unrequested wording.
