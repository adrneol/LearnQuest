## PHASE 3 — MAKE GOOGLE REGISTRATION STRICT

Google must remain the only registration method.

The intended user journey is:

1. The user explicitly selects Create an account.
2. LearnQuest starts a genuine Google OAuth/OIDC flow.
3. The backend validates the identity response, issuer, audience, expiry, nonce, OAuth state, and verified Google email.
4. Identity is bound to Google's stable `sub`, not email alone.
5. The user completes onboarding with a unique username, display name, and password.
6. The account and login session are established only after the correct server-side flow has completed.

### Registration restrictions

- Never allow someone to register by merely typing an arbitrary email address.
- Never trust a client-supplied Google email, Google subject, `email_verified` flag, onboarding identity, or `userId`.
- Do not silently create an account when someone clicks Google sign-in and Google returns an identity that has never registered.
- Google login intent and Google registration intent must remain distinct and protected by single-use server-validated OAuth state.
- If an existing account attempts registration, do not create a duplicate account.
- A Google identity already linked to an account must not be linked to another account just because the email matches.
- Enforce normalized unique username and email constraints in the database.
- Ensure onboarding can only be completed for the specific short-lived, server-validated Google authentication transaction that initiated it.
- Prevent replay, account takeover, email-linking vulnerabilities, and session fixation.

For an unknown Google identity arriving through the login flow, provide a safe failure and an explicit route back to Create an account. Do not silently switch login into registration.

Preserve password sign-in for accounts that have completed Google registration and onboarding. Google-only registration does not mean password login must be removed.

Write end-to-end-style tests using mocked Google OIDC responses for:
- New Google identity attempting login.
- New identity deliberately registering.
- Existing Google identity signing in.
- Existing identity trying to create a duplicate account.
- Unverified email.
- Invalid audience, issuer, nonce, expiry, state, and replayed state.
- OAuth identity not matching the server-side onboarding transaction.

## PHASE 4 — REMOVE ALL NUMERIC OTP AUTHENTICATION

I explicitly do not want LearnQuest's six-digit Brevo OTP recovery flow.

### Replace OTP with secure, single-use email action links

Keep Brevo as LearnQuest's transactional email provider, but replace numeric password-recovery and email-change verification with secure, single-use email action links.

Implement:

- Cryptographically random, high-entropy opaque tokens; never sequential or predictable tokens.
- A digest or HMAC of each token in the database, not the raw token.
- Purpose binding, account binding, and email-address binding where applicable.
- Short configurable expiry enforced by the server.
- Atomic single-use consumption so concurrent requests cannot reuse a token.
- Rate limiting, resend cooldowns, anti-replay handling, and appropriate invalidation of previous active links.
- Generic password-recovery responses that do not reveal whether the account exists.
- Safe invalid, expired, already-used, and malformed-link states.
- Password validation and Argon2id password hashing on the backend.
- Revocation of existing sessions after a successful password reset, with a fresh login required.
- Verification of a new email before replacing the account's existing verified email.
- A security notification to the previous email address when an email change succeeds, where appropriate.
- No sensitive tokens in ordinary server logs, analytics, exception messages, or email-provider diagnostic output.

Prefer a reset link that carries the token in the URL fragment and exchanges it through an explicit POST after the reset page loads. Remove the token from browser history as early as practicable. Do not consume tokens through a GET request that may be automatically opened by email security scanners.

Use appropriate `Cache-Control: no-store` and `Referrer-Policy: no-referrer` behavior for sensitive recovery pages. Avoid third-party resources on pages handling reset tokens.

Ensure password-reset completion cannot be called successfully without the correct, valid, unused token.

Inspect existing reset-grant and challenge collections before choosing a migration. Remove obsolete OTP code without breaking account storage or unrelated learning data. Rename obsolete configuration only where necessary, preserve existing secrets, and document any new environment variable the owner must configure.

Do not manufacture environment secrets. If a dedicated email-action HMAC secret is introduced, generate it securely, never print it, and explicitly document the local and production configuration required.

Add tests for expired tokens, replay, concurrent consumption, purpose mismatch, account mismatch, token leakage prevention, generic responses, resend limits, and session revocation.
